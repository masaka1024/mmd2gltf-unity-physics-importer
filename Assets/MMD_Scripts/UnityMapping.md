# Unity / lilToon への写し方

`extras.mmd` の**データの意味**は
[エクスポーター側の仕様書](https://github.com/masaka1024/mmd2gltf-gui/blob/v1.2.0/mmd2gltf/extrasMmd_schema.md)
が正本です。このファイルは、それを **Unity（URP + lilToon）でどう実装したか**を
記録します。仕様ではなく実装事項なので、エクスポーター側には持ち込みません。

---

## 描画順（renderQueue）

仕様側の要求は「材質番号順の合成を保つこと」です。Unity では以下の2帯構成で
実現しています（Tda式ミクV4X・IA で実証済み）。

| alphaClass | キュー | 理由 |
|---|---|---|
| `"mask"`（`origTexture` で半透明へ昇格したもの） | AlphaTest帯 `2452 ＋ 材質番号` | 深度を書きつつ、真の半透明より先に描画する。透け髪やレンズ越しの物体が正しく見える |
| `"blend"` | Transparent帯 `3000 ＋ 材質番号` | MMD の材質順合成を再現する |

`origTexture` があるものを一律に Transparent（3000）へ昇格させると、透明キュー内が
サブメッシュ番号順になるうえ TwoPass が深度を書くため、**前髪より後番号の
メガネ・レンズが前髪の深度に落ちて消えます**（Tda式ミクV4X で実測）。
共有テクスチャを使うモデルは全マテリアルが `origTexture` を持ちうるため、
昇格の条件を `alphaClass` で分けることが必須です。

## マテリアル

| extras.mmd | lilToon | 備考 |
|---|---|---|
| `sphereMode` = 1 | 乗算スフィア | PMX 標準の並び（1=乗算, 2=加算）。仕様書の記載と実装が逆だった時期があり、黒潰れの原因になった |
| `sphereMode` = 2 | 加算スフィア | |
| `sphereMode` = 3 | 未対応 | サブテクスチャ。MatCap の誤適用を防ぐため警告ログを出してスキップ |
| `toonTexture` | 個別トゥーン | glTF `textures[]` の番号だが Unity 側サブアセット順とは一致しないため、**名前で照合**する |
| `toonShared` | 共有トゥーン | MMD 標準の `toon01`〜`toon10.bmp` をプロジェクト内からファイル名検索して自動割り当て（利用者が用意する） |

### 実装上の注意

- `lilToon.Editor` アセンブリは `autoreferenced: false` のため `using lilToon` が
  使えません。型名文字列によるリフレクションで
  `lilToonInspector.SetupMaterialWithRenderingMode` を呼びます。
- 同メソッドは `isoutl` 引数を明示しないとアウトライン込みの実体シェーダーに
  切り替わりません。3引数の簡易オーバーロードは ambient static に依存して
  不安定なため、**全引数を明示する7引数版**を使います。
- UniGLTF は標準マテリアルスロットから参照されない画像（トゥーン / スフィア）を
  テクスチャアセット化しません。GLB の bufferView を直接辿って生画像を抽出し、
  新規アセットとして保存する必要があります。
- `ambient` / `specular` / `specularPower` は未対応です。lilToon に MMD の
  specular に相当する色付きハイライトのプロパティがなく、近似の効果が
  軽微と判断して保留しています。

### 陰影オーバーレイの濃さ

眉・まつ毛まわりのオーバーレイは、MMDよりやや薄いほうが好まれる場合があるため、
半透明画素（α&lt;250）のみを `tune_semiAlphaFactor` 倍に減衰させるスライダーを
用意しています（既定 0.7、肌の不透明画素は不変）。

## UniGLTF 側の既知の制約

- **モーフターゲットの sparse 形式を正しく読めません。** 口パクのモーフが
  別部位の変形として現れる症状が出ます。エクスポート時に
  `morph_mode="dense"` を指定してください（UniGLTF 前提のモデルは dense を標準に）。

## 物理の写し方（Rigidbody + ConfigurableJoint）

MMD/Bullet の設定を PhysX へ持ち込むときに実際につまずいた点の記録。
データの意味は
[エクスポーター側の仕様書](https://github.com/masaka1024/mmd2gltf-gui/blob/v1.2.0/mmd2gltf/physicsGltf_schema.md)
が正本で、ここに書くのは Unity 側の実装事情。

### まず `physicsGltf` を使う

`rigidBodies` / `joints`（raw）は PMX 生値・未スケール・オイラー角なので、
インポーター側でスケール推定・座標変換・オイラー順序の解釈が必要になる。
`physicsGltf` は `unitScale` 適用済み・クォータニオン・ボーンローカルなので、
そのどれも要らない。raw を使うと次の2つを踏む。

- ジョイントの移動制限を PMX 原単位のままメートルとして設定してしまう
  （`unitScale=0.08` なら **12.5倍緩い**。スカートの横リングがほぼ無拘束になる）
- PMX のオイラー順序は YXZ、Unity の `Quaternion.Euler` は ZXY。
  さらに glTF 軸への鏡映も要る

### glTF → Unity の座標系変換を忘れない

`physicsGltf` は glTF（右手系 Y-up）で書かれている。UniGLTF は読み込み時に
**Z反転**（位置 `(x, y, -z)` / 回転 `(-x, -y, z, w)`）してボーン階層を作るので、
剛体・ジョイントのオフセットにも同じ変換が要る。

掛け忘れると位置は微妙に、回転ははっきりずれる。実測ではカプセルの長軸と
ボーンの向きの角度差が **平均46°（最大86.8°）→ 変換後 平均10.2°**（一部は 0.0°）だった。

**角度制限も鏡像を通す**必要がある。X軸まわりは符号が反転するので、
`low` と `high` を入れ替えて符号を反転する（Y/Z は絶対値の最大を採るなら影響なし）。

PMX 自体は Unity と同じ左手系 Y-up なので、PMX→glTF→Unity で2回反転して元に戻る、
というのが本来の姿。

### 衝突は PMX のマスクをペア単位で再現する

剛体名でレイヤーを振り分ける方式では作者の指定を再現できない。
IA の実測では **6786組中 1446組だけが衝突**、つまり**指定の79%が失われていた**。

判定は双方向で `(1<<A.group & B.mask) && (1<<B.group & A.mask)`。
**立っているビットは「そのグループと衝突する」**（PMXエディタのチェック表示とは反転）。

`Physics.IgnoreCollision` はシーンに保存されないため、再生のたびに貼り直す
コンポーネントが要る（`MmdCollisionMask`）。

> PMX仕様書のフィールド名は「非衝突グループフラグ」で、本文にビットの意味の記述がない。
> 名前だけ読むと逆に解釈しやすく、そうすると揺れ物が毎フレーム押し出されて発散する。
> 「Unityでは無理」という結論に着地しやすい落とし穴。

### 揺れ物の根元は体に埋まっているのが前提

MMD のモデルは、髪の根元やスカートの中段が体のコライダーの内側に入った状態で
静止姿勢が作られている。IA では**62〜109組が静止姿勢で食い込み**（平均0.024m／最大0.13m）。

これは解消すべき侵入ではないので、押し出すと再生と同時に外へ弾かれる。
起動時に食い込んでいる組はいったん衝突対象から外し、**離れた時点で本来の衝突に戻す**
（そのままにするとモーション中にすり抜ける）。

### 再生開始1フレーム目の姿勢差に注意

バインドポーズとモーション先頭の姿勢が違うと、再生した瞬間に Kinematic な体のボーンだけが
新しい姿勢へ飛ぶ。揺れ物は取り残され、ジョイントは1ステップで巨大な誤差を突きつけられる。
IA では **1.0m の拘束誤差 → 角速度 3741 rad/s** の爆発になり、収まるまで11秒かかった。

対策は単純で、最初の 0.2 秒ほど揺れ物を Kinematic のままにし、アニメーションが姿勢を
確定させてから物理へ引き渡す（`MmdPhysicsWarmup`）。拘束誤差ゼロから始められる。

**この症状は接触が原因に見える**（衝突を切ると止まるため）が、接触は爆発したエネルギーの
伝達経路でしかない。接触側をいくら柔らかくしても直らない。

### ドライブは剛体の慣性で正規化する

MMD のジョイントは**バネ定数が 0**（IA では72個全数）で、MMDは限界内では完全に自由。
ただし PhysX でそのまま 0 にすると閉ループを含む構造が保たない。何らかの安定化が要る。

ここで**一律のバネ定数を与えてはいけない**。髪のカプセルの慣性は `1.6e-5`、
スカートの箱は `2.0e-4` と一桁以上違うので、同じ数値でも効き方がまるで変わる。
実際、髪が落ち着く値ではスカートが全く広がらず、スカートが動く値では髪が発散した。

意味があるのは戻ろうとする速さ `ω = √(k/I)` なので、
**`k = I·ω²`、`c = 2ζ·I·ω`** とすれば全身で振動数と減衰比が揃う。
調整は「速さ(Hz)」と「減衰比ζ」の2つだけになる。

同じ理由で、**ダンパーに固定の下限を置いてはいけない**。
`Mathf.Max(spring * 0.1f, 0.5f)` のような下限は、慣性 `1e-5` の髪に対しては
時定数が `1e-5` 秒相当になり、相対回転が瞬時に消えて親へ溶接されたような硬さになる。
重力を変えても硬さが変わらないのが見分け方。

### 効果がなかった／逆効果だったもの

- **ジョイントの投影**（`projectionMode`）— 1つの剛体に複数の拘束が付く閉ループでは
  発動し続け、毎フレームの強制移動がエネルギー源になる。時間刻みを細かくするほど悪化する
- **`sleepThreshold = 0`** — スリープが微振動を吸収していたぶん、切ると初期発散が出る
- **Fixed Timestep を粗く**（60Hz）— 硬い拘束が多い系では悪化。**0.0083（120Hz）**が良好

### スケール由来の落とし穴

- **`contactOffset`** — PhysX の既定 0.01m は、`unitScale=0.08` で取り込んだ髪のカプセル
  （半径 6mm）より太い。接触の余裕が形状自身より大きいという逆転が起きるので、
  剛体自身の寸法から決める
- **重力** — MMD の物理は PMX の単位系で動いている。長さだけ `unitScale` 倍して重力を
  据え置くと、振り子の周期が `√0.08 ≒ 0.283` 倍になり **MMDより3.5倍速く揺れる**。
  重力も同じく `unitScale` 倍すれば周期が一致する
